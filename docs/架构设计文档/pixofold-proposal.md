# PixoFold（轻图）项目方案

调研日期：2026-09-20；工程更新：2026-09-23。状态：继续采用 GPL-3.0-or-later。静态PNG、批量/导入、应用协调、订阅及受控原生选择已通过三平台CI（584d1e9）。本轮接通P4最小真实PNG工作台及主页面重载撤销；拖放、自选输出目录、缩略图和其他格式待实现。新代码检查、原生GUI实际验收、1412告警及未验证范围见devlog，不沿用旧CI。

界面迭代入口：[HTML 交互原型](../UI界面设计/PixoFold.html) 与 [原型说明](../UI界面设计/HTML原型说明.md)。HTML 用于先行确认 UI 和操作流程，演示处理器不代表真实压缩实现。

## 项目定位与推荐结论

将 png-palettes 演进为本地运行的批量图片压缩工具 PixoFold，中文名确定为「轻图」。Pixo 关联像素，Fold 表达收拢体积；名称不绑定某一种图片格式。仓库与可执行文件建议命名为 `pixofold`，核心 crate 命名为 `pixofold-core`。

方案继续采用现项目的 GPL-3.0-or-later，保留 imagequant 作为 PNG/APNG 有损量化核心，Windows 优先验证，同时维护 macOS 和 Linux 桌面构建。第三方组件保留各自许可证。

在独立的 pixofold 仓库中采用新的 Tauri 2 工程结构，保留能够验证正确的算法经验、语言文案和素材，迁移时记录来源并保留相应版权与许可声明，重建文件处理、任务调度、IPC 和前端状态管理。旧 png-palettes 项目保留为行为参照和性能基线，本方案统一在 pixofold 的 docs 目录维护。

目标是可靠地处理 PNG、JPEG、GIF，并保留 APNG 支持。首个完整版本聚焦原格式优化；格式转换、WebP、AVIF、目标体积搜索和命令行发行版作为后续扩展。

## Tauri 升级可行性

可以升级。当前项目只有一个主要业务命令 `compression_handle`，压缩核心已经独立于 Tauri，框架耦合较小。真正需要投入的是业务重构和格式兼容性，而不仅是依赖版本修改。

官方提供从 Tauri 1 到 2 的迁移指南和辅助命令。此次建议使用 Tauri 2 的稳定系列作为目标，构建时锁定通过测试的版本。调研时官方发布页列出的 runtime 为 2.11.5，JS API 为 2.11.1，CLI 为 2.11.4；这些组件的版本号不必完全一致。[官方发布页](https://v2.tauri.app/release/)

迁移项目包括：

- 重新整理 `tauri.conf.json`，将旧 allowlist 转成按窗口和插件声明的 capabilities。
- 将 `invoke` 导入迁移到 `@tauri-apps/api/core`，文件选择改用 dialog 插件，外部链接和打开所在目录使用相应的 opener 能力。
- 更新窗口、拖拽、构建路径与环境变量的使用方式；移除对旧窗口阴影库的硬依赖，按各平台实际效果选择实现。
- 将 `main.rs` 缩减为启动入口，应用初始化、命令注册与服务状态放入 `lib.rs` 及独立模块。
- 通过 Rust 自定义命令执行图片读写，对任务 ID、输入路径和输出目标做后端校验。capabilities 不能代替这些业务校验。
- 使用Tauri Channel发送有界revision变化通知，进度和结果通过权威快照查询；先建立订阅并读取初始快照再启动任务，界面重新挂载时恢复显示而不重跑任务。
- 配置 CSP 和受限的预览资源访问；前端无需获得任意文件读写或任意进程执行能力。

[Tauri 1→2 迁移指南](https://v2.tauri.app/start/migrate/from-tauri-1/)、[Channel 文档](https://v2.tauri.app/develop/calling-frontend/)、[Capabilities 文档](https://v2.tauri.app/security/capabilities/)

## 图片引擎选型

解码、颜色量化和压缩优化是不同职责。`imagequant` 负责生成调色板，`png` 负责编解码，`oxipng` 负责无损优化；三者通过格式适配器组合。继续使用 GPL 后，无需为了许可调整而更换现有量化核心。

| 格式与模式       | 首选实现                                    | 处理原则                                                                                           |
| ---------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| PNG 无损优化     | oxipng 10.x                                 | 优化过滤、压缩及可逆表示；默认不修改完全透明像素中的 RGB 数据                                      |
| PNG 有损压缩     | png 0.18.x + imagequant 4.4.x + 可选 oxipng | 解码并处理颜色信息，生成带透明度的调色板，编码后执行适度无损优化                                   |
| JPEG 无损优化    | MozJPEG 的 jpegtran 路径                    | 在压缩系数层优化，不经过普通解码再编码                                                             |
| JPEG 有损压缩    | MozJPEG，经 Rust 适配层封装                 | 提供质量、色度采样、渐进式编码设置；保留可替换后端接口                                             |
| GIF 无损优化     | Gifsicle 独立工具                           | 优化帧差分和调色板结构，验证播放效果、时间轴及循环次数                                             |
| GIF 有损压缩     | Gifsicle 的 lossy 选项                     | 统一质量值反向映射为允许误差；默认不降帧、不缩放、不额外减色                                       |
| APNG 无损优化    | oxipng + png 检查与验证                     | 支持范围受 oxipng 的 APNG 优化能力限制                                                             |
| APNG 有损压缩    | png + imagequant 共享调色板                 | 重新实现并验证帧合成、透明、位移和播放语义，不直接搬运旧的动画处理逻辑；验证未通过前只开放无损路径 |
| 格式探测与缩略图 | image-rs/image 等基础组件                   | 负责公共图像操作，不取代专用的压缩优化路径                                                         |

### PNG：保留并升级 imagequant 与 png，补充 oxipng

调研时文档展示 `imagequant 4.4.1` 和 `png 0.18.1`。imagequant 4 已是 Rust 实现，支持带透明度的调色板量化；png 提供纯 Rust PNG/APNG 编解码。现项目只接受 RGBA 是应用层分支限制，不是 PNG 库只支持 RGBA。实施时锁定通过回归测试的版本。[imagequant](https://github.com/ImageOptim/libimagequant)、[imagequant API](https://docs.rs/imagequant/latest/imagequant/)、[png API](https://docs.rs/png/latest/png/)

`imagequant`/libimagequant 官方提供 GPLv3+ 与商业双重许可。本项目选择 GPLv3+ 路线，保留并使用其开源实现，按 GPL 要求提供对应源码及许可声明。[imagequant 官方许可说明](https://pngquant.org/lib/)

量化目标质量由统一的 0–100 质量值映射，默认「高」档为 80；速度和抖动放入高级选项，计算强度与画质分别控制。用固定语料验证升级前后的画质、体积和性能。PNG 调色板质量不达标时保留无损结果或原图，并报告原因；不得静默丢弃透明度或将透明图铺底。

PNG 应扩展到 RGB、RGBA、灰度、灰度透明和索引色输入。16-bit 图片默认进入保留位深的无损路径；降为 8-bit 调色板属于有损转换，应由明确选项控制。

oxipng 适合补充当前缺失的无损路径。它也能优化 APNG，但官方说明该支持有限，不能等同于完整动画结构优化；`alpha` 优化会修改透明像素的 RGB，不应放进严格像素无损预设。[oxipng 官方说明](https://github.com/oxipng/oxipng)

2026-09-22 实现基线：锁定 oxipng 10.2.1 与 png 0.18.1，关闭 oxipng 的 binary / parallel / zopfli 默认功能，使用单线程 preset 1、30 秒软期限及解压上限。严格路径禁止位深、色型、调色板、灰度和 alpha reduction，并保持原始交错方式。由于 oxipng 仍会整理 tRNS 和 chunk 顺序，适配器只采用其 IDAT，其余 chunk 原样保留，再重新解码比较像素与全部非 IDAT 数据；不支持改写的未知 unsafe-to-copy 元数据直接拒绝。APNG 在完整 chunk 扫描时拒绝，不能仅依赖首帧头信息。实际样本及参数见 [PNG 核心归档](../devlog/_fin/260922/png-core-foundation.md)。

同日有损实现：锁定 imagequant 4.4.1 并关闭默认 threads，适配器借助 png 展开 RGB/RGBA/灰度/索引色，映射版本 1 为 min=0、target=q，独立固定 speed=4、dither=1.0。对 remapping 实测评分再做 q 阈值检查；评分不足、alpha 保护失败或产物不比源文件及无损候选更小，选择严格无损并报告原因。alpha=0/255 必须保持，半透明仍为 1–254 且最大误差 8；有损不保证隐藏 RGB。16-bit、ICC/cHRM/cICP/HDR、表示相关 sBIT/bKGD/hIST/sPLT 不进入量化，不隐式转换颜色或降位深。有效 gAMA 使用相同输入/输出 gamma；与 sRGB 冲突则回退。适用元数据保留原字节及 IDAT 前后位置。量化产物重新解码对比调色板/索引，再经公共输出层的落盘、复查、备份和提交；实现、基线及限制见 [PNG 有损归档](../devlog/_fin/260922/png-lossy-quality.md)。

### JPEG：先以 MozJPEG 落地，对 Jpegli 做实测

MozJPEG 适合作为初版基线，提供有损编码和 jpegtran 无损优化路径。`quality=100` 的普通 JPEG 重编码仍不能替代无损优化。[MozJPEG](https://github.com/mozilla/mozjpeg)

Rust mozjpeg 包装库明确说明部分错误通过 panic/unwind 传播。因此适配边界必须处理 unwind，相关构建不得使用 `panic=abort` 来假装可恢复；任务监督逻辑必须把异常转成失败终态。需要硬取消和更强进程隔离时，转为受控工作进程，不宣称 `catch_unwind` 能捕获原生崩溃。[mozjpeg-rust](https://github.com/kornelski/mozjpeg-rust)

Jpegli 是值得优先验证的替代方案，输出仍是兼容 JPEG 的文件。Google 的研究报告显示其在特定高质量比较中有优势，但不能据此承诺任意旧 JPG 都再缩小固定比例。先用同一素材集比较相近观感下的体积、耗时、内存、ICC 和三平台构建情况；若收益足够，再更换默认有损编码器。无损 JPEG 路径独立保留。[Jpegli](https://github.com/google/jpegli)、[Google 的研究与测试说明](https://opensource.googleblog.com/2024/04/introducing-jpegli-new-jpeg-coding-library.html)

### GIF：使用 Gifsicle 独立工具

Gifsicle 原生面向已有 GIF 的结构优化，并提供有损模式，适合当前压缩需求。打包固定版本的官方源码构建产物，通过受控子进程调用；用户不需要另行安装命令行工具。使用普通命令行参数和 GIF 文件交换输入输出，保持独立程序边界。Tauri 支持把外部程序作为 sidecar 随应用分发。[Gifsicle](https://www.lcdf.org/gifsicle/)、[参数手册](https://www.lcdf.org/gifsicle/man.html)、[Tauri sidecar](https://v2.tauri.app/develop/sidecar/)

Gifsicle 主程序采用 GPL-2.0-only，应用采用 GPL-3.0-or-later，不能把两者直接链接或合并后统一标为 GPLv3。按独立程序随包分发的设计落实各自许可，记录通信方式、源码来源、构建脚本和版本，发布前核查独立性与分发义务。[Gifsicle 官方声明](https://github.com/kohler/gifsicle#copyrightlicense)、[GNU 关于组合与聚合的说明](https://www.gnu.org/licenses/gpl-faq.en.html#MereAggregation)

gifski 更适合从高质量帧序列或视频生成 GIF，不作为已有 GIF 的默认压缩器。其开源许可为 AGPL-3.0-or-later；后续评估视频转 GIF 时，需重新评估集成与分发方式，不把它视为普通 GPLv3 库自动引入。[gifski 官方说明](https://gif.ski/)、[gifski 许可清单](https://github.com/ImageOptim/gifski/blob/main/Cargo.toml)

前端保留 React、TypeScript、Vite、CSS Modules，升级到实施时兼容的稳定版本。使用 Zustand 存放任务视图和界面设置，替换模块级可变 `works`；语言、主题、压缩模式、最近一次有损质量值通过版本化配置持久化。采用一个包管理器和一个前端锁文件，并固定 CI 的 Node/Rust 工具链。[Zustand](https://github.com/pmndrs/zustand)

Rust 核心库不依赖 Tauri、React 或窗口对象。编码适配器接收源数据、格式参数、进度/取消上下文及临时输出目标，返回结果描述；只有输出层能够提交最终文件。不得为了统一接口而把所有输入都先变成 RGBA：JPEG 无损优化、PNG 无损优化和 GIF 结构优化应保留各自路径。

Rust 是任务状态的权威来源，前端仅维护展示快照。请求/响应由命名字段组成，替换旧的无字段名 tuple 事件。可使用 ts-rs 从 Rust DTO 生成 TypeScript 类型，并在 CI 检查生成结果；运行时仍需检查参数范围和状态合法性。[ts-rs](https://github.com/Aleph-Alpha/ts-rs)

2026-09-23 P3b首步落地桌面ipc模块：只读get_task_snapshot在一次TaskControl快照上转换摘要和一页jobs/candidates/issues，每页1–100行；翻页须携带同一应用revision，过期拒绝且从第一页恢复，不把不同版本拼接。u64标识/版本/字节/毫秒使用精确十进制字符串，计数转换检查范围，未知大小保留null。展示名限制240字符且仅取末级文件名，标明截断/替换/控制字符清理；错误按稳定枚举转换，底层错误和原生路径不跨边界。只读命令不建立路径授权，不触发任务。协议版本与页面上限随Rust类型生成，保留原核心生成文件；前端单页读取器拒绝迟到或回退快照，销毁不取消后台任务。

P3b第二步实现subscriptions模块：应用唯一SubscriptionRuntime与通知线程复用TaskControl，最多一个主窗口会话。首次subscribe返回protocolVersion/subscriptionId/revision票据，前端查询后确认才开始Channel投递；每会话一条在途通知，变化合并而不排队。ACK精确匹配会话/版本，重复最近ACK不解锁新版，旧会话的取消不影响替换后的会话。投递/释放Channel均在锁外；发送失败清除对应会话，不取消任务。没有订阅/等待ACK/任务Closed无新版本时休眠，等待任务变化时用100ms超时兼顾控制响应；常规退出同时停止接纳、取消任务并在唯一后台收尾路径join通知/任务线程。

前端TaskSnapshotSubscription限制页面单连接，通知后只读取所选集合第一页并确认，保留最后好快照；其他分页仍用TaskSnapshotReader保证同revision。disconnect屏蔽迟到结果，后续connect以查询恢复终态，没有自动无限重试或传输存活探测。锁定SDK的Channel没有公开close，正常清理由Rust drop/end帧完成；首次响应失败且会话ID未知时保留单个页面槽并要求重载，已知会话清理失败可重试disconnect，不能调用私有SDK回调接口。该边界不等于自动重连，原生WebView恢复还需单独验收。

不在Rust持锁时序列化整批数组，也不承诺交付每个中间阶段。分页不保留历史版本，活跃批次全量遍历可能失效，应限制到可见页并在终态恢复。

P3b第三步由Rust侧tauri-plugin-dialog取得文件/目录路径，应用唯一NativeImports槽最多一个物理对话框或一份授权（1000根、路径总编码长度1 MiB、5分钟惰性过期）。前端只持grantId/rootCount；路径不经过JS输入或响应，新选择替换旧授权，成功导入单次消费，授权与已ACK的订阅会话绑定。对话框等待在槽位接纳后的后台执行，旧页面回调不得给新页面发授权；关闭先撤销授权，SDK无显式关闭对话框接口的边界及原生退出验证单独记录。

主窗口新增select_native_import与apply_task_mutation两个命令，不授予通用dialog/fs/event权限。变更在订阅→授权槽→任务锁序内短时接纳，无I/O/await；start/cancel/clear复验selection，retry复验批次revision和有界唯一失败/取消行ID，沿用Rust原行输出，不重跑成功项。命令适配依赖IPC DTO/错误转换、授权槽与任务服务，IPC模型不反向依赖授权槽，核心不依赖Tauri。输出先限覆盖/同目录副本；自选目录授权和受控拖放后续独立实施，不接收任意路径字符串。

TaskActions复用已握手的TaskSnapshotSubscription，最多一个在途操作，固定点击时的参数；选择过程中断开/替换后的迟到响应不能自动启动，写操作响应失败不自动重发。接纳票据不是完成结果，继续由快照恢复实际状态。

P4最小工作台由页面唯一WorkspaceController所有，复用一个订阅/TaskActions及一个额外分页查询；React重挂载、语言/主题切换不重新构造任务。合法设置单独持久化，临时质量文本不保存，非法设置导入只扫描；本页修正后自动启动，后台规划拒绝后同设置不循环，重载Ready需主动修改设置。页面只保留订阅首屏和当前可见页，每页50项，同revision查询，过期回首屏；重试只选本页失败/取消稳定ID并沿用后端输出授权。大小/状态/回退/恢复名均来自权威DTO，不复用HTML模拟。compressionAvailable现为true，语义仅为至少一种格式已接通，目前仅静态PNG，不代表全部规划格式。

main页面Started在订阅锁域内移除旧会话并撤销原生授权，Channel锁外释放；未返回的物理对话框标记失效但保留槽，晚到结果由permit拒绝/释放，不创建第二个选择窗口。锁序保持订阅→授权，既有TaskRuntime/任务快照不变；Finished及其他页面加载不撤销。此路径不依赖WebView卸载回调成功送达。

### 质量控制与主题边界

- 前端 `QualityControl` 用同一个整数 `quality` 驱动 0–100 连续滑块和下方输入框；质量描述由该数值派生，不分别保存三个可能冲突的状态。默认值为 80，描述为「高」。
- Rust 核心提供 `QualityValue` 校验和按格式解析的质量映射；PNG、JPEG、GIF、APNG 共用界面尺度，但各自转换为适配器参数。映射带版本号，解析后的参数和输入质量值一起进入任务快照。
- 当前只落地 PNG 映射与 Rust/TS 判别类型；`PngMode` 的无损变体没有 q，反序列化拒绝额外字段和非整数/越界值。开发 API 的 `PngRequest::new` 默认无损以兼容旧调用，正式产品默认有损 80 仍待界面接入，不能把这些规划组件当作已实现。
- 启动批次时固定模式、质量值、映射版本、计算强度和输出策略。运行中更改设置只影响后续批次，不改变已经排队的任务。
- 无损模式走独立路径，不向编码器传入有损质量参数；界面保留最近的有损质量值，切回有损模式后恢复。100 是有损质量尺度的上限，不自动等同于无损。
- 亮暗主题由语义化 CSS 变量控制，任务状态、质量值与文件列表不随主题切换重置。交互、映射和验收细节见 [UI 交互与质量映射设计](ui-interaction-design.md)。

### 任务、并发与取消

2026-09-22 P1已实现：任务服务位于独立核心 `batch::BatchService`，不再计划在桌面壳中重复维护一份权威队列。只接收显式文件列表，以标准库固定worker、VecDeque与Condvar调用单文件pipeline；同步只读预检、编码和join均不持状态锁。公开模型是Rust领域快照（非IPC DTO），批次ID在服务内单调、行ID在批次内稳定，attempt/revision区分重试与旧变化。后续Tauri仅负责生命周期装配、DTO转换及订阅，不让React销毁承担任务清理。

默认1 worker/1000行/4GiB估算预算，工作集按请求的输入、解码和像素上限保守预留，单项超预算失败、总预算不足等待；不是RSS硬限额或预分配，未经实测不提高默认并发。启动时整批检查重复输入、硬链接、输出冲突和输出指向其他输入；源/目标仍须在提交前复查，预检不消除外部路径竞争。Windows比较键保守折叠大小写，其他平台不存在目标的大小写别名可能在提交阶段才被拒绝。

取消后未开始项立即结束，运行项等真实返回才进入终态并归还预算；越过提交临界点的成功不被令牌改写。wait超时只是停止等待；shutdown/Drop自主取消并join。重试只选失败/取消项，固定新参数/目标并保留已完成项；清除/换批不删除产物和恢复备份。单项panic归为结果未知的失败，锁故障停止接纳。汇总只计算成功收益，未知字节数不假设为0。验证与后续入口见 [批量桌面记录](../devlog/_plan/260922/png-batch-desktop.md)。

P3a已实现应用协调：桌面只创建一个TaskRuntime，TaskControl可克隆但不拥有线程，不因窗口重载或前端销毁释放任务。协调器在单槽门闩下执行扫描、规划、启动、重试和清除；核心BatchService仍是唯一编码调度/行状态来源，没有第二份可独立变化的行队列。输入清单及批次通过Arc只读快照展示，SelectionId阻止跨导入误操作，重试还校验批次revision；待参数修正时保留完整清单，部分扫描不允许启动。

协调线程执行全部同步文件I/O/预检，状态锁只做短更新；活跃批次以100ms采样核心变化，空闲等待通知，P3b订阅等待应用revision。采样与通知都只提供最新状态，不是逐事件日志；终态由权威查询恢复，不以Channel发送成功证明前端已消费。默认设置在应用层明确为有损80/覆盖，核心开发默认无损不变。

共享取消令牌贯穿导入与核心start_with_cancel/retry_with_cancel：准入前取消不入队、不改变旧attempt；入队后继续按真实流水线结果选终态。核心取消公布状态与revision一起更新，重复观察取消不持续唤醒worker。新增BatchError::Cancelled需完整match调用方补分支。Tauri常规退出先禁止接纳，后台唯一收尾任务join全部线程后才允许退出；OS强杀/断电/重启恢复不在保证范围。任务DTO与权限尚未开放，具体API见 [README](../../README.md)。

以下为完整任务链的目标与约束；其中核心调度/扫描、应用退出、桌面订阅和原生选择授权已落地，拖放授权、自选输出目录及多格式仍待实现：

- 每批任务拥有 batch ID，每个文件任务使用独立 job ID；事件带序号和阶段，前端可以忽略过期更新。
- 扫描、排队、处理、验证、提交是可观测阶段；成功、跳过、失败、取消是终态。每个任务恰好进入一个终态。
- 先注册 Channel 再启动任务，并提供查询快照命令。窗口重载不应使后端任务失去管理。
- 使用有界工作队列，异步部分处理协调和 I/O，CPU 编码在专用线程池运行。移除反复遍历列表的忙循环。
- 文件并行和编码器内部并行共享总预算，避免外部每核一个任务、内部每任务再开满所有核心。
- 根据图像尺寸、位深和帧数估算解码内存，限制同时执行的高内存任务；限制尺寸、帧数、累计解码字节，动画尽量分阶段或使用磁盘中间缓存。
- 可协作取消的编码器使用回调；不支持中断的调用显示「取消中」，返回后丢弃结果，并在提交前再次检查。受控子进程可以终止。不能把超时停止等待误当作计算已经停止。
- 按固定频率合并进度更新，例如每任务每秒最多约 10 次；成功/失败等终态立即发送。没有真实百分比的编码器显示处理阶段，不伪造进度。

## 文件处理与数据正确性

### 导入和格式识别

2026-09-22 P2 已落地纯 Rust 调用链：`import::scan` → `ImportScan::plan` → `BatchService::start` → `pipeline/output`。扫描不创建线程池或写产物，后续文件选择、目录选择及拖放由 Tauri 统一送入有界后台入口，不在 UI 线程扫描/预检。

- 按真实内容识别静态 PNG，不用扩展名排除候选；检查全部 chunk/CRC 与头部声明的资源上限，但不展开像素。APNG 明确拒绝；JPEG/GIF/WebP 等仅返回不支持反馈，后续引擎接入后再开放。CRC 正确的坏像素数据仍会在 pipeline 完整解码时失败。
- 规范化路径与已接受候选的文件身份去重；根列表保留用户顺序，目录内排序，首次归属确定输出布局。不跟随枚举到或显式根叶节点的链接/Windows reparse；显式祖先别名仍沿用 canonicalize 边界，不宣称这是路径沙箱。身份句柄仅扫描期间持有，返回前关闭。
- 默认最多 1000 根/1000 候选/10000 条目/32 层目录/累计读取 1 GiB，单文件默认 64 MiB；遍历用有界待处理集合，每条目和 64 KiB 读取边界协作取消。进度报告实际计数和已读取字节，不虚构百分比；OS 调用或单次 CRC 不能硬中断，也没有进程 RSS 硬限额承诺。
- 单个目录无权限、文件损坏或格式不支持时明确反馈并继续；空输入返回空结果，不创建批次。取消或达到全局上限产生不可启动的部分结果，不隐式压缩前 N 个文件。仅完整清单可规划，参数/目标错误不消耗清单，修正后可重试；清单固定路径与归属而非锁住源内容。
- 扫描完成才允许输出；默认按统一保留名排除 PixoFold 临时/备份文件，显式 `include_artifacts` 可包含。该规则不是来源证明，合法文件恰好使用保留名也会收到排除反馈；不笼统排除隐藏图片或 `_compressed` 副本。保留名和配置范围见 [README](../../README.md)。

输出规划支持覆盖、原目录副本、指定目录扁平或保留根结构。副本统一为 `stem_compressed.png`；保留结构映射为 `目标/导入根名/相对父目录/副本名`，单独文件置于目标根，文件系统根用 `_root`。不同根同名、输出重名、输出与输入交叉或计划文件兼作另一输出父目录均在只读预检拒绝。规划复用 batch 准入实现，不创建第二套冲突规则；start 和最终提交仍复查。取消原生对话框、文件授权和实际桌面映射留在 P3。

### 输出提交协议

默认原图覆盖，通过「原图覆盖 / 另存副本」分段切换选择输出策略。原图覆盖使用输入文件原路径，并沿用下述备份和可靠提交协议；另存副本时才显示输出目录设置，可指定目录并保留目录结构。模式与最近副本目录分别持久化，切换时不清空目录；副本目录、目录结构和同名策略仅在副本模式生效。

P2 新增显式 `OutputPolicy::CopyTree { root, relative }`：root 必须是已存在目录，relative 只接受普通相对组件；规划只读，仅 output 暂存时逐级创建必要结构目录，复查链接/类型，最终副本仍 noclobber。旧 `Copy` 仍要求父目录存在，不暗中改变调用方权限或副作用。结构目录是持久输出布局，取消/失败/无收益可能留空，不自动删除以免与其他 worker 竞争；临时文件仍按原协议清理。Rust 下游完整 match 需补新变体，IPC/TS DTO 不受本次影响。

1. 记录输入身份及必要指纹，规划输出路径，并处理同名冲突。
2. 在目标目录创建独占的临时文件，编码器只写临时产物。
3. 完成编码器收尾、缓冲区 flush 和所需的文件同步。
4. 重新打开输出，检查格式、尺寸、动画与元数据；按模式执行必要的正确性验证。
5. 计算最终文件大小。默认仅接受体积更小且通过验证的结果，否则标记「无收益，保留原文件」。
6. 再次检查取消状态、输入是否被外部修改及目标冲突。需要覆盖时先按策略建立可恢复备份。
7. 使用经过各平台验证的替换操作提交；进入提交临界区后不强行中断。无法可靠替换时保留原图并报告原因。

不能把任意两次重命名都称为原子提交，也不能假设一个通用 rename 调用在所有 Windows/网络文件系统场景都具有相同语义。输出层需要平台测试，且不得使用「先删原文件再写新文件」的回退方案。

当前单文件实现采用 tempfile 的同目录独占临时文件和 persist / persist_noclobber，输入通过句柄身份、大小、修改时间和完整内容复查；临界区前再次检查实际候选文件和备份。覆盖总是保留原始备份，副本总是拒绝现有目标。同步文件后再替换，不执行先删源文件的回退；提交失败返回恢复路径，清理失败返回残留路径。Windows NTFS 的正常覆盖及占用失败已测，但没有实现文件系统 compare-and-swap 或目录 fsync，关闭源句柄到替换仍有竞争窗口，也不承诺保留特殊 ACL/ADS/xattr 或断电事务性。无损提交3f6c617及包含有损功能的ab9b2bb均通过三平台CI核心文件测试和桌面构建；这些历史证据不覆盖GUI、网络文件系统、上述特殊属性或新增批量/导入代码，其验证分别见 [连续记录](../devlog/_plan/260922/png-batch-desktop.md)。

### 颜色、元数据与动画

- 元数据策略独立于压缩强度：默认保留影响显示的 ICC、gamma、方向等信息；清除 GPS/设备信息提供独立选项。
- JPEG 有损路径如应用了 EXIF 方向，就同步重置方向标记；ICC 必须与输出像素的色彩空间匹配。
- 对 CMYK JPEG 和广色域输入，先验证完整颜色转换链。未实现可靠转换前可走保留颜色的无损路径，不能静默当作普通 RGB 重编码。
- 严格无损 PNG 保留解码像素值，包括高位深和透明像素的隐藏 RGB；更改这些数据应归入有损或明确命名的额外优化。
- GIF/APNG 按完整合成画面和时间轴验证，覆盖帧偏移、透明、blend/dispose、局部调色板与循环信息。不得只压缩第一帧。
- 任何为了体积而缩放、降帧或降低位深的操作都必须是明确选项。

## 产品交互

参考 png-palettes 的「左侧导入和工作区、右侧参数栏」布局及导入即处理的交互，采用简洁的现代桌面界面。标题栏显示「PixoFold · 轻图」和亮暗主题切换；左侧空闲时显示中央识别区及「选择文件 / 选择目录」，导入后在同一区域切换为全部图片列表；底部加高并固定，无有效图片时展示操作技巧，有图片时切换为汇总和总进度。右侧集中显示压缩模式、质量和输出位置，不显示开始压缩按钮。亮暗两种主题保持相同结构与交互。

导入并识别完成后自动启动压缩。默认选择「有损压缩」，所有支持格式统一使用 0–100 连续质量滑块，下方提供整数输入框。数值越高表示保留画质的倾向越强，不表示压缩率越高，也不承诺跨格式的感知画质完全相同。

| 质量描述 | 数值范围 |
| --- | --- |
| 低 | 0–29 |
| 较低 | 30–49 |
| 中 | 50–69 |
| 高（默认值为 80） | 70–84 |
| 较高 | 85–94 |
| 最高 | 95–100 |

滑块按数值线性移动，不吸附到六个预设值，也不显示档位圆点或下方标签；当前描述仅在「压缩质量」标题行右侧以无边框、无背景的纯文字显示，位置与原设计一致。例如输入 76 后，滑块移动到 76%，描述为「高」，实际质量保持 76。描述区间是本项目的交互设计约定，后端映射单独按格式校准。

压缩模式只保留「有损压缩 / 无损优化」两个入口。有损模式下质量控制可用；无损模式下将滑块与数值框禁用，并提示「无损模式保留原始画质」。原「均衡压缩 / 体积优先」不再作为与质量滑块并列的第二套入口。速度、抖动、色度采样和计算强度等格式设置放入「高级选项」。

输出设置采用与压缩设置一致的「原图覆盖 / 另存副本」分段切换，默认「原图覆盖」，此时收起目录设置。选择「另存副本」才显示现有输出目录控件，默认输出到原文件夹并自动使用 `_compressed` 文件名后缀；同名冲突仍走统一输出策略，也可选择其他目录。再次切回副本模式时恢复之前的目录。

拖入或选择文件/文件夹后，递归识别并对本次导入去重，参数有效时自动启动压缩；没有支持图片时反馈识别结果，参数无效时保留已识别文件并等待修正。中央列表逐张展示缩略图、文件名、原始大小、输出大小、减少比例和状态。桌面底部汇总至少约 170 CSS px，固定显示文件总数、总体积变化、累计节省量、各状态计数和总进度条，列表独立滚动。只有成功项计入节省量，其余文件保留原始大小参与总量统计。处理过程中暂不接收新批次；结束后可重试未完成文件或直接导入下一批。HTML 中只执行假压缩模拟，用于验证交互与显示。

底部在列表为空时显示批量导入、参数设置和快捷操作技巧，隐藏零值统计与空进度条；有效图片进入列表后显示汇总，参数待修正、完成或取消时继续保留，清除结果后恢复技巧。没有支持的图片时，技巧与识别反馈同时保留。两种视图共用底部容器，桌面端保持区域高度与位置稳定。

初版应包含：多文件/目录/拖拽导入，文件去重，批量队列，取消和失败重试，连续质量滑块与精细输入，输出目录，前后体积比较，静态缩放对比，动画播放检查，中文/英文，亮暗主题与设置持久化。详细交互见 [UI 交互与质量映射设计](ui-interaction-design.md)，设计图见 [UI 界面设计](../UI界面设计/README.md)。

图片列表按任务标识更新发生变化的行，避免每次进度更新重建整个列表或改变滚动位置；正式工程对大列表使用虚拟化。缩略图按需生成并缓存，前端访问受限资源 URL，不再把全部原图转为 Base64 经事件广播。当前 HTML 展示原图缩略图和模拟体积结果，不提供压缩后像素对比或行菜单。

## 旧问题对应的重构措施

| 现有问题                                    | 对应措施                                           |
| ------------------------------------------- | -------------------------------------------------- |
| `File::create` 直接覆盖输入，写入失败难恢复 | 临时产物、输出验证、收益比较、可靠提交和可选备份   |
| 线程内 `unwrap()` 可能使任务没有完成消息    | 结构化错误、任务监督、原生包装库异常边界、终态保证 |
| 调度器无限轮询任务与通道                    | 有界工作队列和阻塞/异步消息接收                    |
| 文件监听未注销，窗口监听在渲染时重复注册    | IPC 服务统一管理订阅生命周期和迟到的异步注册结果   |
| 拖拽回调捕获旧压缩参数                      | 统一提交入口，每批提交时生成不可变参数快照         |
| 多目录导入重复追加整个工作列表              | 后端统一扫描、去重、生成 job ID 并一次建立任务集合 |
| 前端模块变量与 React 状态并存               | Rust 权威状态、前端单一展示 store、不可变更新      |
| `WorkListType` 重复且字段类型不同           | Rust DTO 生成 TS 类型，命名事件数据，协议版本校验  |
| 取消目录选择仍可能提交 `null`               | 导入层统一校验取消与空输入                         |
| 只允许 RGBA，不区分位深                     | 格式探测及按模式选择处理路径                       |
| 整图 Base64 预览占用大                      | 按需缩略图、受限资源访问和缓存回收                 |
| 进度与终态分离可能乱序                      | 任务内事件序号，提交完成后确定最终成功状态         |
| 缺少自动化用例                              | 图像语料、故障注入、端到端操作和平台打包测试       |

## 验证与发布

- PNG 语料：RGB、RGBA、灰度、索引色、透明边缘、渐变、8/16-bit、交错图、ICC/gamma。
- JPEG 语料：baseline/progressive、灰度、ICC、CMYK、EXIF 方向 1–8、已高度压缩图片。
- 动画语料：局部帧、帧偏移、多种 dispose/blend、透明背景、局部调色板、不等长帧延时及循环控制。
- 文件故障：只读目录、文件被占用、磁盘写入失败、长路径、中文/特殊字符路径、重复路径、符号链接和外部修改。
- 任务故障：扫描失败、编码器错误/退出、处理中取消、取消与提交竞争、界面重新挂载、批量中部分失败。
- 无损路径验证格式相应的不变量；动画比较合成后的时间轴画面，不能只比较文件字节或原始帧数量。
- 有损路径结合相近视觉质量下的体积、SSIM/感知指标和人工检查；透明边缘与动画闪烁不能仅由单一指标判定。
- 性能报告记录环境、引擎版本、参数、耗时分位数、峰值内存与输出体积，不预先承诺固定压缩百分比。
- 质量交互验证：默认值 80、连续滑块和输入框双向同步、0/100 边界、质量描述区间、非法输入提示、无损模式禁用与恢复，以及混合格式任务共用质量值但独立映射参数。
- 质量映射验证：PNG/APNG 的目标值、JPEG 原生质量、GIF 反向 lossiness 映射均在有效范围内；最高档不能被标记为通用无损。每批任务保留映射版本，运行中改动设置不会改变已有任务。
- 主题交互验证：亮暗模式布局一致，文本与焦点可读，标题和质量描述无挤压或截断，键盘可操作；主题切换不重置任务和数值，重启后恢复偏好。
- CI 执行前端类型检查/测试/构建，Rust format/clippy/test，以及三平台构建和打包后的基本运行验证；核心图像回归不依赖图形界面。
- Tauri 原生 UI 自动化按平台能力选择，不假设同一 WebDriver 链路覆盖全部系统；前端可用模拟 IPC 做组件测试，平台对话框/拖拽另做集成验证。
- 发布时固定外部二进制版本及校验信息，记录依赖许可证、工具链和构建来源；签名与自动更新放在发行准备阶段完成。
- 发布前核对各包的 GPL-3.0-or-later 声明，并按三平台最终依赖和安装包生成第三方清单。为对应发行版本提供完整对应源码和必要构建资料，独立工具按自身许可证提供源码及通知；核查 GPLv2-only、GPLv3+ 和 AGPL 组件的组合方式。

## 扩展顺序

后续优先考虑静态 WebP、明确的格式转换、限制最大尺寸、目标体积搜索，再评估 AVIF、视频转 GIF 和 CLI。目标体积搜索须每次从原始输入重新编码，避免把多轮有损结果串联处理。

保留独立核心库和格式适配器后，这些能力可以增量添加，而无需再次改写界面和任务系统。
